## 1. نظرة عامة

نظام Desktop يعمل بالكامل Offline لإدارة: المنتجات، المخزون، العملاء، الموردين، المبيعات، المشتريات، التحصيلات، مدفوعات الموردين، الخزينة، المرتجعات، تسويات المخزون، مع لوحة تحكم وتقارير. الهدف الجوهري: **أي عملية واحدة (بيع/شراء/تحصيل/دفع) تُحدِّث تلقائيًا وذريًا كل الأطراف المتأثرة** (المخزون + حساب العميل/المورد + الخزينة + سجل التتبع) دون أي خطوة يدوية إضافية من المستخدم — هذا هو "Core Business Logic" المذكور في البند 39 من الـPRD ويجب أن يبقى ثابتًا طوال التطوير.

## 4. القرارات المعمارية المقفولة 🔒

| القرار | التفاصيل والمبرر |
|---|---|
| **State Management** | Cubit (`flutter_bloc`) — نفس منهجية مشاريعك السابقة، طبقات غير مربوطة بالأداة |
| **قاعدة البيانات المحلية** | **Drift** (فوق `sqlite3`) وليس `sqflite` الخام. المبرر: يدعم Desktop عبر `NativeDatabase`، يوفر Streams تفاعلية (مثالية لـDashboard/Cubit)، Type-safe queries، ودعم Transactions ذرية أصيل. *(قرار مشروعك السابق بمنع Drift كان خاصًا بسياق SaaS Online-First مختلف تمامًا — هنا النظام Offline بالتعريف فالمنطق ينعكس تمامًا)* |
| **الأموال (Money)** | تُخزَّن كـ **`int`** بوحدة "قرش" (1 جنيه = 100 قرش). **ممنوع `double` نهائيًا لأي مبلغ مالي.** الجمع/الطرح على أعداد صحيحة = دقة مطلقة بدون أخطاء تقريب Floating-Point |
| **الكميات (Quantities)** | تُخزَّن كنوع **`Decimal`** (package: `decimal`) عبر `TypeConverter` في Drift (محفوظة كـ TEXT في SQLite). ممنوع `double` لأي كمية مخزون — الوحدات المختلفة (كيلو/جرام/لتر/قطعة) تحتاج دقة كسرية مضمونة |
| **المفاتيح الأساسية** | `Integer Autoincrement` وليس UUID — مبرر: جهاز واحد، لا حاجة لمعرّفات عالمية، أداء وبساطة أفضل. *(تكلفة معروفة: أي مزامنة مستقبلية بين أجهزة تتطلب هجرة لاحقة لـUUID — مقبولة الآن وفق مبدأ YAGNI)* |
| **DI** | `get_it` (Service Locator بسيط، بدون `injectable` إلا إذا كبر المشروع) |
| **التنقل** | `go_router` |
| **الطبقة المرجعية للتحقق** | لا يوجد Backend/RLS هنا؛ **طبقة الـDomain (UseCases) + قيود الـDatabase Transaction هي المرجع النهائي**، والتحقق في الـUI هو لتحسين تجربة المستخدم فقط (نفس روح "Untrusted Client" لكن بآلية محلية) |
| **الذرية (Atomicity)** | كل عملية مركّبة (بيع/شراء/تحصيل/دفع/مرتجع/تسوية/رصيد افتتاحي) تُنفَّذ داخل `db.transaction()` واحدة في طبقة الـRepository، تُستدعى من UseCase واحد. فشل أي خطوة = تراجع كامل، لا حالة جزئية أبدًا |
| **سجل التتبع (Audit Log)** | يُكتب تلقائيًا **داخل نفس الـTransaction** لكل عملية تُغيّر بيانات، لا كخطوة منفصلة قد تُنسى |
| **عدم الحذف النهائي** | لا حذف فعلي لمنتج/عميل/مورد (إيقاف فقط status)، ولا حذف/تعديل مباشر لعملية بيع/شراء قديمة — الإلغاء يتم عبر "عكس/مرتجع" جديد يُسجَّل بأثر رجعي مرئي (البند 33 من الـPRD) |
| **اللغة** | عربي بالكامل RTL فقط. **لا بنية ARB ثنائية اللغة** (لا حاجة لها بلا لغة ثانية) — نصوص مركزية في ملف Dart واحد `app_strings.dart` لمنع التكرار العشوائي، وليس لأغراض ترجمة |
| **الوضع الليلي** | غير مبني في V1 (افتراض قابل للتغيير) — Tokens التصميم تجعل إضافته لاحقًا رخيصة |
| **البناء والحماية** | `flutter build windows --release --obfuscate --split-debug-info=./build/symbols` لكل إصدار يُسلَّم للعميل |

## 5. البنية الطبقية (Clean Architecture)

```
┌─────────────────────────────────────────────────────────┐
│ Presentation  → Widgets/Pages + Cubit/State              │
│   يعرض فقط، يستمع لـCubit، ممنوع أي منطق أعمال هنا       │
├─────────────────────────────────────────────────────────┤
│ Domain        → Entities + Repository Interfaces + UseCases │
│   Dart نقي 100%، بدون Flutter وبدون Drift إطلاقًا          │
├─────────────────────────────────────────────────────────┤
│ Data          → Models + Drift DAOs + Repository Impl     │
│   تحوّل صفوف Drift ↔ Domain Entities، تفتح الـTransactions │
└─────────────────────────────────────────────────────────┘
```

قاعدة صارمة: **الـDomain لا يستورد `package:drift` ولا `package:flutter` مطلقًا.** أي كسر لهذه القاعدة = فشل مراجعة الكود.

## 7. نموذج البيانات الكامل

> ملاحظة عامة: `amount`/`price` كلها `int` (قرش). `quantity` كلها `Decimal`. كل الجداول تحمل `created_at`، والجداول القابلة للتعطيل تحمل `is_active`.

### 7.1 products
| الحقل | النوع | ملاحظات |
|---|---|---|
| id | int PK | autoincrement |
| name | text | مطلوب |
| code | text? | اختياري، فريد إن وُجد |
| unit | text | "كيلو/جرام/لتر/قطعة/كرتونة/عبوة..." — نص حر يُتحقق منه بالـDomain، لا Enum صارم بقاعدة البيانات (سهولة إضافة وحدات جديدة) |

## 8. التدفقات الذرية للعمليات المركّبة (تنفيذ حرفي لقواعد 1-8 في الـPRD)

كل تدفق أدناه = UseCase واحد يستدعي Repository واحد يفتح `db.transaction()` واحدة.

### 8.1 إنشاء عملية بيع (البند 12/35)
1. تحقق أن الكمية المطلوبة ≤ `current_quantity` لكل منتج *(انظر قرارًا مقترحًا أدناه)*.
2. إدراج صف `sales` + صفوف `sale_items` (مع Snapshot السعر).
3. لكل صنف: إدراج `inventory_movements` (sale, سالبة) + تحديث `products.current_quantity`.
4. إن كان هناك مبلغ متبقٍ: إدراج `customer_ledger_entries` (increase) + تحديث `customers.current_balance`.
5. إن كان هناك مبلغ مدفوع فورًا: إدراج `cashbox_transactions` (in) + تحديث رصيد الخزينة الحالي.
6. إدراج صف `audit_log` (create/sale).
7. Commit — أو Rollback كامل عند أي فشل.

> **⚠️ قرار مقترح يحتاج تأكيدًا (لم يذكره الـPRD صراحة):** هل يُمنع البيع إذا تجاوزت الكمية المخزون المتاح، أم يُسمح بترحيل سالب (Overselling) مع تنبيه فقط؟ **الافتراض الحالي: منع افتراضي + خيار "تجاوز مقصود" يتطلب تأكيدًا إضافيًا من المستخدم في نفس الشاشة.**

### 8.2 إنشاء عملية شراء (البند 17-18/36) — نفس تدفق البيع بعكس الاتجاه (مخزون +، خزينة -، حساب مورد +)

### 8.3 تحصيل من عميل (البند 14-15)
1. إدراج `customer_payments` (مع `linked_sale_id` اختياري).
2. إدراج `customer_ledger_entries` (decrease) + تحديث `customers.current_balance`.
3. إدراج `cashbox_transactions` (in) + تحديث رصيد الخزينة.
4. `audit_log`.

### 8.4 دفع لمورد (البند 20) — نفس تدفق 8.3 بعكس الاتجاه (خزينة out، حساب مورد decrease)

### 8.5 مرتجع من عميل (البند 25)
1. إدراج `returns_customer` + أصناف المرتجع.
2. لكل صنف: `inventory_movements` (customer_return, موجبة) + تحديث المخزون.
3. تعديل `customer_ledger_entries` (decrease بقيمة المرتجع) + تحديث الرصيد.
4. `audit_log`.

### 8.6 مرتجع لمورد — عكس 8.5 (مخزون ينقص، حساب المورد يُعدَّل)

### 8.7 تسوية مخزون (البند 26)
1. إدراج `stock_adjustments` (مع `reason` إلزامي).
2. إدراج `inventory_movements` (adjustment) + تحديث `products.current_quantity`.
3. `audit_log`.

### 8.8 إلغاء/عكس عملية سابقة (البند 33)
لا Overwrite أبدًا. يُنشأ سجل "عكس" (reversal) جديد بنفس آلية البند المعني (بيع/شراء) بقيم معكوسة، ويبقى السجل الأصلي مرئيًا بحالة `reversed`.

## 9. الوحدات والشاشات

| المبيعات | نموذج بيع (متعدد الأصناف) · قائمة · تفاصيل فاتورة · شاشة إلغاء/عكس |

## 10. لوحة التحكم والتقارير (البند 28-29)

**Dashboard:** استعلامات تجميع تعمل عبر `Stream` (Drift يُعيد البث تلقائيًا عند تغيّر الجداول المُراقَبة) لعرض: مبيعات/تحصيلات/مشتريات/مدفوعات موردين/رصيد خزينة اليوم + إجمالي ديون العملاء + إجمالي مستحقات الموردين + تنبيهات مخزون منخفض + آخر العمليات.

**التقارير الستة:** مبيعات · تحصيلات · عملاء · موردون · مخزون · خزينة — كل تقرير = Repository مخصص بفلاتر تاريخ إلزامية لمعظمها، ونتائج قابلة للفرز.

## 11. استراتيجية النسخ الاحتياطي والاستعادة (البند 2/34)

- ملف قاعدة البيانات يقع في مسار بيانات التطبيق (`path_provider` على Windows) — اسم ملف واحد ثابت.
- **نسخ يدوي:** المستخدم يختار مجلدًا (`file_picker`) فيُنسخ ملف الـDB بتسمية `backup_YYYYMMDD_HHmm.sqlite`.
- **تصدير لـUSB:** نفس آلية النسخ اليدوي، الفرق فقط في المسار المختار من المستخدم.
- **نسخ تلقائي دوري:** عند إغلاق التطبيق أو أول تشغيل يومي، نسخة إلى مجلد نسخ داخلي مع سياسة احتفاظ (الاحتفاظ بآخر N نسخة، حذف الأقدم).
- **الاستعادة:** يختار المستخدم ملف نسخة → تُؤخذ نسخة أمان من القاعدة الحالية أولاً (قبل الاستبدال) → يُتحقق من `schema_version` المخزّن في `backups_meta` → استبدال الملف → إعادة تشغيل التطبيق.
- منع فقد البيانات المفاجئ: كل عملية كتابة تمر عبر Transaction، فلا توجد حالة نصف مكتوبة حتى عند انقطاع الكهرباء أثناء الحفظ.

## 12. سجل التتبع (Audit Log — البند 27)

كل UseCase يُغيّر بيانات يُدرج تلقائيًا صفًا في `audit_log` **ضمن نفس الـTransaction** (وليس كخطوة لاحقة منفصلة قد تُنسى أو تفشل بمعزل عن العملية الأصلية). الهدف: يستطيع المستخدم دائمًا معرفة "كيف وصل النظام إلى هذا الرقم؟".

## 15. استراتيجية الاختبار

- **Domain:** اختبارات وحدة Dart نقية على UseCases، بمحاكاة (`mocktail`) لواجهات الـRepository.
- **Data:** اختبارات على Repository/DAO باستخدام `NativeDatabase.memory()` (قاعدة بيانات في الذاكرة) للتأكد من صحة كل Transaction (خصوصًا تدفقات §8).
- **Presentation:** `bloc_test` لكل Cubit + اختبارات Widget للنماذج الحرجة (البيع/الشراء/التحصيل).
- **يدوي:** سيناريو مكتوب لكل ميزة قبل الانتقال للتالية (إلزامي حسب `AGENT_RULES.md`).
